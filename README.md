# @b4moss/calengine — 仕様書
## 1. 概要
`@b4moss/calengine` は、カレンダー UI に必要な日付演算、カレンダーグリッド生成、予定の配置計算などを提供する、UI 非依存の TypeScript ライブラリである。
カレンダーの演算ロジックをレンダリング層から分離し、複数の UI 実装やバックエンドから再利用できるようにする。
将来的に Go へ移植することを想定し、特定の言語やランタイムに依存しない仕様とデータモデルを採用する。
## 2. パッケージ構成
### 2.1 calengine
npm パッケージ名: `@b4moss/calengine`
担当する機能:
- 日付・期間の演算
- タイムゾーンを考慮した日付処理
- 月間・週間カレンダーグリッドの生成
- 週番号の計算
- 予定の期間計算
- 複数日にまたがる予定の分割・配置計算
- 同時刻に存在する予定の配置計算
- 期間選択に必要な日付範囲の処理
- 休日情報を扱うための日付モデル
### 2.2 final-calendar
npm パッケージ名: `@b4moss/final-calendar`
担当する機能:
- HTML / CSS によるカレンダーの描画
- 年・月・週ビューの表示
- 予定の作成・編集 UI
- ドラッグ＆ドロップによる予定の移動
- ドラッグによる予定のリサイズ
- 日付範囲の選択 UI
- ユーザー操作のイベント通知
`final-calendar` は `calengine` を利用する。`calengine` は `final-calendar` に依存しない。
## 3. 設計原則
1. DOM、HTML、CSS、ブラウザ API に依存しない。
2. React、Vue などの UI フレームワークに依存しない。
3. 日付演算とレンダリングを分離する。
4. 外部ライブラリへの依存は必要最小限にする。
5. TypeScript と Go で同じ仕様を実装できるようにする。
6. ロケール依存の表示文字列を演算結果に含めない。
7. 現在時刻を暗黙的に参照しない。必要な場合は呼び出し元から渡す。
8. 暗黙のタイムゾーン変換を避ける。
9. 入力値の変更やグローバル状態への依存を避け、可能な限り純粋関数として実装する。
10. 仕様として確定していない動作を独自判断で実装せず、未確定事項を明示する。
## 4. 日付・時刻モデル
日付と日時を明確に区別する。
### 4.1 LocalDate
タイムゾーンや時刻を持たない暦日を表す。
```ts
interface LocalDate {
  year: number;
  month: number; // 1-12
  day: number;
}
```
用途:
- 日単位の予定
- カレンダーの各日付
- 休日
- 日付範囲の指定
### 4.2 LocalDateTime
タイムゾーンを持たないローカル日時を表す。
```ts
interface LocalDateTime {
  date: LocalDate;
  hour: number;
  minute: number;
  second?: number;
  millisecond?: number;
}
```
用途:
- ローカル時刻として入力された予定日時
- タイムゾーンを適用する前の日時データ
  
### 4.3 Instant
UTC 基準の絶対時刻を表す。
TypeScript では Unix epoch milliseconds などの明示的な表現を使用する。
```ts
type Instant = number;
```
Go への移植時には `time.Time` などに対応させる。

### 4.4 TimeZone
IANA Time Zone Database のタイムゾーン識別子を使用する。
例:
- `Asia/Tokyo`
- `America/New_York`
- `Europe/London`
タイムゾーンの変換は明示的な操作とし、ローカル日時から Instant への変換では、DST による存在しない時刻や重複する時刻の扱いを規定する。

### 4.5 日付範囲
日付範囲は原則として半開区間 `[start, end)` とする。
```ts
interface DateRange {
  start: LocalDate;
  end: LocalDate;
}
```
`start` は範囲に含み、`end` は含まない。
この方式により、隣接する期間の境界を統一的に扱える。
日時の範囲も同様に半開区間とする。
## 5. カレンダー設定
```ts
interface CalendarConfig {
  timeZone: string;
  weekStartsOn: number; // 0: Sunday ... 6: Saturday
  locale?: string;
  firstWeekContainsDate?: number;
}
```
- `timeZone` はカレンダーの基準タイムゾーン。
- `weekStartsOn` は週の開始曜日。
- `locale` は必要に応じて曜日名などの表示側で利用する識別子。
- `firstWeekContainsDate` は週番号の規則を定義するための設定。
週番号の計算方式は明示的に指定できるようにする。ISO 8601 方式をサポートし、その他の方式は要件に応じて追加する。
設定値の有効性は検証する。

## 6. 基本的な日付演算
次の操作を提供する。
- 日付の妥当性検証
- 日付の比較
- 日数の加算・減算
- 月の加算・減算
- 年の加算・減算
- 月初・月末の取得
- 週初・週末の取得
- 曜日の取得
- 月の日数の取得
- うるう年判定
- 日付間の日数計算
- 2 つの日付範囲の重複判定
- 日付範囲の交差部分の取得
- 指定期間に含まれる日付の列挙
月・年の加算で対象日に対応する日が存在しない場合の処理を明示する。
例: 1 月 31 日に 1 か月加算した場合の結果は、仕様で定めた規則に従う。暫定的には対象月の末日に丸める方式を採用する。

## 7. カレンダーグリッド

### 7.1 月間グリッド
指定した年月と設定から、月間カレンダーのグリッドを生成する。
入力:
```ts
interface MonthGridInput {
  year: number;
  month: number;
  config: CalendarConfig;
}
```
出力:
```ts
interface CalendarDay {
  date: LocalDate;
  weekday: number;
  isCurrentMonth: boolean;
  isToday?: boolean;
  isWeekend: boolean;
  isHoliday: boolean;
}
interface CalendarWeek {
  weekNumber: number;
  days: CalendarDay[];
}
interface MonthGrid {
  year: number;
  month: number;
  weeks: CalendarWeek[];
}
```
要件:
- 週の開始曜日に従って列を並べる。
- 前月・翌月の日付を必要に応じて含める。
- すべての週は 7 日で構成する。
- グリッドの週数は固定値とせず、表示規則に基づいて決定する。
- 休日情報がない場合、休日判定は未判定として扱える設計にする。
- 「今日」の判定が必要な場合、基準日を呼び出し元から渡せるようにする。
- 
### 7.2 週間グリッド
指定した日付を含む週のグリッドを生成する。
要件:
- `weekStartsOn` に従って週の開始日を決定する。
- 7 日分の `CalendarDay` を返す。
- タイムゾーンや週の開始曜日を変更しても一貫した結果を返す。
- 
### 7.3 年間ビュー用データ
年間ビューで利用するため、指定年の 12 か月分のグリッドを生成できるようにする。
月間グリッドの生成処理を再利用し、年間ビュー専用の独立した日付演算を重複実装しない。

## 8. 予定データモデル
予定データは UI の表示形式から独立させる。
```ts
interface CalendarEvent {
  id: string;
  title?: string;
  start: number;
  end: number;
  allDay: boolean;
}
```
`start` と `end` は Unix epoch milliseconds を表す。
要件:
- `start < end` を必須とする。
- 終了時刻は排他的とする。
- 終日予定と時刻指定予定を区別する。
- 予定の永続化、API 通信、認証、認可は担当しない。
- 表示用の色、フォント、DOM 要素などを必須フィールドにしない。
- 予定の ID の生成は担当しない。
終日予定を表現する場合、日付と Instant のどちらを正規のデータモデルに採用するかは、実装前に確定すること。終日予定の日付がタイムゾーン変換でずれない設計を優先する。

## 9. 予定の配置計算
予定の配置計算は、レンダラーが必要とする構造化データを返す。
対象機能:
- 表示期間と予定期間の重複判定
- 表示期間外にはみ出した予定の切り詰め
- 複数日にまたがる予定の分割
- 週境界をまたぐ予定の分割
- 同時刻に重なる予定のグルーピング
- 同一時間帯の予定に対する配置レーンの割り当て
配置結果には少なくとも次の情報を含める。
- 元の予定 ID
- 表示対象の期間
- 予定の開始・終了
- 複数日にまたがる予定の先頭・末尾判定
- 同時刻の予定を区別するためのレーン番号
- レーン数など、レンダリングに必要な配置情報
ピクセル単位の位置やサイズ、CSS クラスは返さない。それらはレンダラーの責務とする。
レーン割り当ての優先順位や同順位の予定の並び順は、決定的な結果になるよう規定する。

## 10. 期間選択
UI に依存しない日付範囲処理を提供する。
対象機能:
- 2 つの日付から期間を生成する。
- 開始日と終了日の前後関係を正規化する。
- 指定した期間が別の期間と重なるか判定する。
- 期間の交差部分を取得する。
- 指定期間を別の期間に制限する。
マウス操作、タッチ操作、キーボード操作などのイベント処理は担当しない。

## 11. 休日
休日データの取得や外部 API との通信は担当しない。
休日情報を受け取り、日付に対して休日かどうかを判定するためのインターフェースを設ける。
休日データの取得元、日本固有の祝日計算、振替休日、国民の休日などの規則は、必要に応じて別モジュールで実装する。

## 12. API 設計方針
- 公開 API は明示的な関数として提供する。
- 設定を必要とする処理は設定を引数として受け取る。
- 入力オブジェクトを変更しない。
- 戻り値の構造を安定させる。
- 不正な入力は明確なエラーとして扱う。
- 暗黙のグローバル状態を持たない。
- 可能な限り純粋関数とする。
- 公開 API と内部実装を分離する。
- 内部実装の都合で公開 API を増やさない。
関数名や具体的なエクスポート構成は実装時に提案し、既存仕様との整合性を確認して決定する。

## 13. Go への移植
将来 Go 版を実装する際、TypeScript 固有の型や実行環境に依存しない仕様を共有する。
共有対象:
- 日付演算の規則
- 週番号の計算規則
- 月間・週間グリッドの生成規則
- 日付範囲の境界規則
- 予定の重複判定
- 複数日にまたがる予定の分割規則
- レーン割り当て規則
- エラー条件
JSON で表現可能な入出力を優先し、共通テストケースを用意する。
TypeScript と Go で同じ入力に対して同じ論理的な出力を得られることを目標とする。タイムゾーンデータベースのバージョン差など、環境依存の差異は明示的に扱う。

## 14. テスト方針
単体テストを中心に、境界値を重点的に検証する。
必須テストケース:
- うるう年と平年
- 月末・年末
- 月をまたぐ日付加算
- 週の開始曜日の変更
- 年をまたぐ週番号
- 月間グリッドの週数
- 前月・翌月の日付の扱い
- 日付範囲の開始・終了境界
- 終了時刻が排他的であること
- 同じ時刻に始まる予定
- 入れ子になる予定
- 複数日にまたがる予定
- 週境界をまたぐ予定
- DST による存在しない時刻・重複する時刻
- 不正な日付や不正な期間
DOM を使用せずにテストできること。
可能であれば、共通仕様を JSON 形式のテストフィクスチャとして管理し、Go 版でも再利用する。

## 15. 非機能要件
- UI フレームワークに依存しない。
- Node.js とブラウザの双方で利用可能な構成を目指す。
- 実行時依存を必要最小限にする。
- TypeScript の型定義を公開する。
- Tree shaking に配慮する。
- 主要な演算は決定的な結果を返す。
- 不要なオブジェクト生成や計算を避けるが、可読性を優先する。
## 16. 対象外
次の機能は `calengine` の責務に含めない。
- HTML / CSS によるレンダリング
- DOM 操作
- マウス・タッチイベントの処理
- UI コンポーネント
- HTTP 通信
- データベースアクセス
- 予定の永続化
- 認証・認可
- 予定の招待・通知
- CalDAV プロトコル
- 外部カレンダーサービスとの同期
- ピクセル単位のレイアウト計算

## 17. Cursor への実装指示
この仕様書をプロジェクトの基準仕様とする。
実装開始前に、仕様の曖昧な点や相互に矛盾する点を列挙する。特に次の事項は、独自判断で確定せず、決定事項として整理すること。
- 日付加算時の月末処理
- 週番号の計算方式
- 月間グリッドの表示規則
- 終日予定の内部表現
- タイムゾーン変換と DST の扱い
- 同時刻の予定のレーン割り当て
- 休日判定のインターフェース
その後、最小限の公開 API とテストから実装を開始する。
一度にすべての機能を実装せず、日付演算、グリッド生成、予定配置計算の順に段階的に実装する。
仕様書にない機能を独断で追加しない。仕様の変更が必要な場合は、変更理由と影響範囲を提示する。
